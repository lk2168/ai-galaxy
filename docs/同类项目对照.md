# 同类项目对照：AI 星图之前，别人已经做了什么

> 用途：给「AI 星图」（纯静态 + YAML 数据 + PR 共建）做定位。
> 原则：**所有事实给出处**；核实不到的写「未核实」，不写 star 数、不写年份猜测。
> 检索时间：2026-10-18。GitHub 数据取自 GitHub REST API（repos 接口），其余给官网/文档链接。

---

## 一、3D / GPU 图渲染库：渲染层已经卷到头了

> 结论先行：这一层**没有任何自研价值**。见第五节。

| 项目 | 它是干什么的 | 许可 | 维护状态（API 实测） | 适合的节点规模 |
|---|---|---|---|---|
| **3d-force-graph** | 用 ThreeJS/WebGL 画 3D 力导向图的 UI 组件，是 `react-force-graph` 3D 模式的底层 | MIT | 未归档；最近推送 2026-09-29；创建于 2017-02；当前版本 1.80.1 | 官方未给出上限。其 large-graph 示例加载 `datasets/blocks.json`，具体节点数未核实 |
| **react-force-graph** | React 封装，支持 2D/3D/VR/AR 的力导向图组件 | MIT | 未归档；最近推送 2026-09-29；创建于 2018-03 | 同上，官方 large-graph 示例的节点数未核实 |
| **sigma.js** | 老牌 2D WebGL 图渲染库，自述「用于可视化数千级节点与边的图」 | MIT | 未归档；最近推送 2026-10-16；创建于 2012-03；v4 已是 TypeScript monorepo（`@sigma/*` 分包） | 官方描述为「thousands of nodes and edges」（数千级），官方文档另设性能专页讨论渲染优化 |
| **cytoscape.js** | 图论/网络分析与可视化库，D3 系之外最通用的 JS 图库 | MIT | 未归档；最近推送 2026-10-15；创建于 2011-08 | 定位为分析型库，官方未宣称百万级；3D 非其主场 |
| **Cosmograph / `@cosmograph/cosmos`** | GPU 加速的力导向布局与渲染库，主打超大规模图；官网 showcase 有 688,335 棵多伦多行道树的 demo | **CC-BY-NC-4.0（非商用）**，商用需单独授权 | npm 最新 3.4.1；GitHub 组织 `cosmograph-org` 下公开的是周边仓库（`cosmos-integrations` 最近推送 2026-07-11），核心源码库 `cosmograph/cosmos` **不存在（404）**，实际分发走 npm | 官网对比页自称：>50K 点可跑力模拟、可渲染 >1M 点与边（**注意：这是厂商自述，非第三方基准**） |

判断依据（这是本节唯一重要的部分）：

1. **MIT 三兄弟（3d-force-graph / react-force-graph / sigma.js）都在活跃维护**，最近推送都在 2026-09 之后（API 的 `pushed_at` 字段），没有「两年没动」的库。
2. **Cosmograph 是陷阱**：许可证是 CC-BY-NC-4.0，`npm` 包里写得很清楚（`registry.npmjs.org/@cosmograph/cosmos`），**非商用**。我们的项目若开源 + 有人想商用，会直接踩线。而且它的 GitHub 核心仓库不存在，等于「只有 npm 产物、没有可审计源码」。
3. 规模上：我们的 AI 星图按历史脉络算，节点量级是**几百到几千**——sigma.js 自称的「数千级」完全覆盖，3d-force-graph 更不在话下。**根本用不到 GPU 百万点那一档**，为了「可能将来很大」去选一个非商用许可证的库，是拿许可证风险换不需要的性能。

## 二、知识图谱 / 星系式可视化产品：它们解决的不是我们的问题

| 项目 | 它是干什么的 | 它解决的问题 | 对我们的意义 |
|---|---|---|---|
| **Obsidian 的 graph view** | 官方核心插件：把 vault 里的笔记画成节点图，节点大小=被链接次数，还有 local graph（只看当前笔记的连接域） | 「我的个人笔记之间是什么关系」——**单机、私有、个人知识管理** | 参考它的 local graph / 深度控制思路；但它没有多人协作、没有外部数据源 |
| **Logseq** | 开源的大纲笔记 + 双向链接知识库，AGPL-3.0，主打 local-first | 同上，个人/小团队知识管理 | 许可证是 AGPL，**传染性强**，网络服务也要开源；只借鉴概念不引代码 |
| **Cosmograph 官网 demo / run.cosmograph.app** | 浏览器里直接上传数据看 3D 图的工具 | 「我手里有一堆点，想最快看到结构」 | 竞品级参考；上面已说许可证问题 |
| **Connected Papers** | 输入一篇论文的 DOI，画出与它最相关的几十篇论文的网络，节点颜色=年份、大小=引用数，数据源是 Semantic Scholar | 「我读一篇论文，想知道该接着读什么」——**围绕单篇论文的探索工具**，不是历史年表 | 它的「相似度算边」做法与我们不同：我们的边是**人工断言的史实关系**，不是算法相似度 |
| **Papers with Code 的图谱** | 曾把论文、代码仓库、benchmark 榜单连在一起，构成「论文→代码→SOTA」的检索基础设施 | 「找某任务的当前最佳成绩」 | ⚠️ **该站 2025 年已下线**（网站下线、跳转到 GitHub 组织，TIB 博客有记述；Hugging Face 后续做了替代但要求模型必须托管在 HF 上）。这是「**依赖单一公司的数据站点会死**」的最佳反面教材 |
| **LYNX（Linked Knowledge Network Explorer）** | 2025 年的会议论文（Zenodo 收录，CC-BY-4.0）：把 Wikipedia/arXiv 的概念做 384 维 Sentence-BERT 嵌入，算语义相似度，在 WebGL 里画成 3D 星系，支持语义搜索与 LOD | 「用语义相似度自动组织海量文献」 | **最接近我们视觉形态的项目**。代码库 `bradene0/lynx` 为 MIT，2025-10 最后推送，star 数 0（API 实测）——学术 demo，非产品。关键差别：**它的边是算出来的，我们的边是人写进 YAML 的** |
| **Wikidata 的可视化** | 对 Wikidata（CC0 的结构化知识库）做图形化查询与展示 | 「机器可读的世界知识底座」 | **数据源参考**：事实类条目（年份、机构、人物关系）可以从这里取，CC0 无传染性；但「AI 发展史」这种带叙事判断的关系，Wikidata 里没有 |

## 三、AI 历史类内容项目：数据从哪来、能不能共建

| 项目 | 它是干什么的 | 数据来源与开放性 | 能否共建 |
|---|---|---|---|
| **AI Index（斯坦福 HAI）** | 年度《AI Index Report》，第八版为 2025 年报告（arXiv:2504.07139），覆盖研发、经济、治理等维度 | 数据来自多源汇编；报告文本在 arXiv 公开，**具体数据的机器可读形式以官网发布为准** | ❌ 不可 PR。它是机构年刊，一年一版，不接受外部条目提交 |
| **Epoch AI 的 AI models 数据库** | 收录 2000+ 机器学习模型，含 notable/frontier/large-scale/all 四个子集，官网可视化 + 每日更新的 CSV 下载 | **数据可下载**（`/data/all_ai_models.csv` 等四个 CSV，页面标注 Oct. 16, 2026 更新）；许可为 **CC BY（署名即可）**；有 GitHub 组织 `epoch-research`（如 `eci-public` 为 MIT） | ⚠️ 半开放。文档明写：想加模型**发邮件到 data@epoch.ai**，不是 PR。数据是「机构维护 + 外部建议」 |
| **各种 AI timeline 网页** | 把 AI 大事记做成时间线/星图的独立网站与 Gist | 各自整理，多数无机器可读数据、无许可证声明 | ❌ 这类正是「**没人管就烂掉**」的重灾区——无数据文件、无贡献入口、无 CI，站点一停就整段历史消失 |

判断：**Epoch AI 的 CSV 是我们最该直接抄的数据源**（CC BY、每日更新、字段规范），AI Index 当背景参照。timeline 类网页证明「只做静态展示、不留数据文件」的项目死得最快。

## 四、「git 即后端」的共建模式：审核成本与腐烂防治

### 4.1 模式样本（API 实测数据）

| 项目 | 它是干什么的 | 许可 | 关键机制 |
|---|---|---|---|
| **awesome-lists（sindresorhus/awesome）** | awesome 列表的「总目录」，收录各类 awesome list | CC0-1.0 | **PR 已改为仅协作者可开**（`pull_request_creation_policy: "collaborators_only"`，API 实测）；仓库描述明写「PR 暂时关闭直到我处理完积压」。有 `awesome-lint`（MIT）做机器校验 |
| **public-apis** | 免费 API 目录，按类别分表 | MIT | 有 CONTRIBUTING.md + PR 模板 + 一个**只校验所有链接有效性**的构建；PR 模板是一串必勾检查项（格式、字母序、描述长度等） |
| **free-programming-books** | 免费编程书籍/课程/播客目录，按语言分子目录 | CC-BY-4.0 | 有 `docs/HOWTO.md`（含中文等 20+ 语言翻译）、PR 走 GitHub Actions 跑 linter；README 挂贡献者增长图鼓励参与 |
| **OpenStreetMap（对照）** | 全球开放地图数据库 | 数据为 **ODbL**（署名-相同方式共享），网站代码 GPL-2.0 | **不是 PR 流**：它有自己的数据库 + 编辑器 + changeset API（`openstreetmap-website` 的 changesets_controller 里有 MAX_ELEMENTS 上限、单用户锁定、一致性校验等）。贡献要注册账号、用 iD/JOSM 编辑器提交 |

### 4.2 从这些项目能直接抄的四条机制

1. **链接/字段校验放 CI，不放人**。public-apis 的构建就是「检查所有链接是否有效」；free-programming-books 提交 PR 会触发 linter。**机器能判的错误绝不占用维护者的肉眼**——这是唯一能让「一个人维护」长期活下来的办法。
2. **PR 模板做成必勾清单**。awesome 的模板要求勾选「无 AI 生成内容」「已读指南」「格式合规」等；public-apis 要求「描述 ≤100 字符」「表列对齐」「已搜索是否重复」。**把规范前移到提交那一刻，比提交后打回成本低一个量级**。
3. **数据腐烂要有自动探测器**。腐烂不是「有人乱填」，而是**链接失效/事实过时没人知道**。对策是定期跑脚本：YAML schema 校验 + URL 可访问性检查 + 交叉引用完整性（引用了不存在的节点 ID 就报错）。
4. **OSM 那条路我们不走**。OSM 是「数据库 + 编辑器 + API」的重架构，维护成本是团队级的。我们的纯静态 + PR 模式成本低得多，**代价是并发编辑能力弱**——这个取舍要认。

### 4.3 「贡献者提交后一年没人管」的项目怎么死的

- **直接死因：积压 + 无反馈**。sindresorhus/awesome 是活化石级的正面样本——它靠的是**把 PR 直接关掉**（collaborators_only），而不是假装能处理完。反面教材是 PR 开着没人看：贡献者等三个月没回音，第二次就不来了；社区没有第二次，数据就静止，一静止就开始腐烂。
- **第二死因：没有「退出机制」**。项目火了 → 条目暴涨 → 维护者 burnout → 停更。free-programming-books 用多语言 HOWTO 把「怎么写条目」标准化，是在降低单条审核成本；我们更极端：**把审核标准写成可执行脚本**，维护者只做脚本判不了的「这条史实对不对」。
- **第三死因：数据不在版本库里**。只在网页上展示、不留 YAML/JSON 源文件的站点，作者一停更就整站蒸发（Papers with Code 是放大版案例）。

## 五、结论：4 条判断

1. **渲染层不用自己写，选 `3d-force-graph`（MIT）**。依据：① MIT 无许可证风险（对比 Cosmograph 的 CC-BY-NC 非商用）；② 2026-09 仍在推送、2017 年至今连续维护；③ 我们的节点量级（数百到数千）落在它和 sigma.js 都轻松覆盖的区间，百万级 GPU 性能是用不到的；④ 我们的项目已经装好了 `3d-force-graph@1.80.1` + React 19，接入成本为零。**sigma.js 作为备选**（2D、MIT、同样活跃），如果将来要 2D 缩略图可以混用。

2. **真正的难点不是可视化，是数据维护与审核**。可视化这层有 5 个成熟 MIT 库任选，两周能出效果；而「贡献者提交后一年没人管」的项目是这样死的：PR 开着没人审 → 贡献者不再来 → 数据静止 → 链接失效、关系过期、新模型没人加 → 站点从「有用」退化成「截图」。awesome 的解法是**关闭 PR 入口**（保质量、弃增长），我们的解法必须是**用脚本把审核成本压到近零**：CI 跑 schema 校验 + URL 活性 + 交叉引用检查，维护者只看「史实判断」这一件事。

3. **我们唯一真正的差异化：把「关系」做成可版本化、可争辩的人工断言**。Connected Papers 的边是共被引算出来的，LYNX 的边是 Sentence-BERT 语义相似度算出来的，Wikidata 没有「影响了谁」这种叙事关系，Epoch AI 只有模型属性表。**我们的 YAML 里每条边都是「某人/某机构在何时因何产生了什么影响」的可审查事实**——错了可以被 PR 推翻、有出处、有 git 历史可追溯。这不是「更好看」，是**别人要么没有边，要么边不可争辩**。

4. **数据源站在 Epoch AI 肩膀上，不站在「自己从头整理」上**。Epoch AI 的四个 CSV 是 CC BY、每日更新、字段规范（`/data/all_ai_models.csv`），AI 模型的年代/机构/算力这类硬事实直接引用它，我们只做它不做的部分：**关系与叙事**。同时把 Papers with Code 的下线当警钟——数据必须留在我们自己的 git 仓库里，绝不只存在于某个第三方服务的网页上。
